What the repository has verified through Phase 3, and what is still planned. Every component is open source and runs on the local Docker Compose stack. There is no cloud deployment path ([ADR-0029](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/decisions/0029-open-source-only-platform.md)). Business logic lives in the Python package; DAGs and Compose files only call it.

## Medallion lakehouse

<DiagramFigure
	light={lakehouseLight}
	dark={lakehouseDark}
	alt="Four tiers from left to right. Raw: Python ingestion writes CSV, JSON and JSONL objects to MinIO. Bronze: Spark appends new complete objects to string-typed Iceberg tables that keep history, duplicates and lineage. Silver: Spark rebuilds typed tables with one row per key. Gold, highlighted: dbt-trino builds facts, dimensions and marts. Layer checks gate each promotion, and Trino reads every layer through the Iceberg JDBC catalog."
	caption="Medallion lakehouse, verified in Phase 2 and scheduled in Phase 3."
	source={`${repo}docs/architecture/phase-2-lakehouse.md`}
/>

- **Raw.** Each ingestion run writes its objects under `raw/{source_id}/{dataset}/dt=…/execution_id=…/` with the source, execution id and ingestion time as object metadata. The same execution overwrites its own objects; a new execution adds new ones ([raw storage layout](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/raw-storage-layout.md)).
- **Bronze.** One Iceberg table per contract, every value stored as text, duplicate keys kept, partitioned by `dt`. A scheduled refresh appends only raw objects of complete executions it has not promoted yet ([Bronze layer](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/bronze-layer.md)).
- **Silver.** Typed and deduplicated, one module per source. A refresh rebuilds only the datasets whose Bronze table changed, and each replace is one Iceberg commit ([Silver layer](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/silver-layer.md)).
- **Gold.** dbt-trino builds facts, dimensions and marts in business-domain schemas, each model a full refresh. A weekly DAG runs the Gold reconciliation checks ([Gold layer](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/gold-layer.md), [Gold model design](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/gold-model-design.md)).
- **Read path.** Trino reads Gold today. JupyterLab notebooks and Superset charts over Gold are planned for Phase 8; the site figures arrive with them.

## Data contracts

Every dataset has a YAML contract under `config/contracts/{source_id}/{dataset}.yaml` that names its grain, primary key, fields, logical types and classification before anything is loaded ([data contracts](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/data-contracts.md)).

- **Invalid rows are kept, not dropped.** The raw object stays whole. Row findings go to a sidecar under `quarantine/`. With `quarantine_exclude`, Silver leaves the row out; with `quarantine_flag`, it keeps the row and marks it. A structural error fails the batch.
- **Counts are recorded.** Silver stores, per dataset, the values a cast turned into null, the rows dropped for a null key and the rows excluded by quarantine.
- **A volume guard** fails a snapshot or full refresh that shrinks below the contract's ratio, unless a run is told to accept it.
- **Update patterns** (`snapshot`, `full_refresh`, `incremental_window`, `append_only`) decide what Silver reads and what a re-run or a deleted source row does.

Table contracts in the ODCS format, checked by the Data Contract CLI, are planned for Phase 10.

## Airflow orchestration

<DiagramFigure
	light={orchestrationLight}
	dark={orchestrationDark}
	alt="Four groups of ingestion DAGs at the top: the daily olist-synth-cdc extract, the weekly re-extract, the DummyJSON and IBGE refreshes, and the manual Olist and storefront loads. Each emits a raw Asset only on success. The Asset, highlighted, triggers transform_lakehouse, which runs Bronze, Silver and Gold in order; each step passes only after its layer check. A weekly reconcile_gold DAG checks Gold."
	caption="Airflow orchestration, verified in Phase 3."
	source={`${repo}docs/architecture/phase-3-orchestration.md`}
/>

Airflow 3.4 runs locally with the LocalExecutor. The DAGs call package entry points ([Phase 3 orchestration](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/phase-3-orchestration.md), [Local Airflow](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/architecture/airflow-local.md)).

| DAG | Schedule | What it does |
| --- | --- | --- |
| `ingest_olist_synth_cdc_daily` | Daily, 00:00 UTC | Extracts the window `[D-1, D)` on `updated_at` in one consistent snapshot |
| `ingest_olist_synth_cdc_weekly` | Monday, 00:00 UTC | Re-extracts `[W-8, W-1)` to pick up commits the daily run missed |
| `ingest_dummyjson_products` | Monday, 03:00 UTC | Full fetch of the product catalog |
| `ingest_ibge_localidades` | Day 1 of the month, 03:00 UTC | Full fetch of municipalities |
| `transform_lakehouse` | On any raw Asset event, one run at a time | Bronze, checks, Silver, checks, quarantine staging, dbt build |
| `reconcile_gold` | Weekly | Gold reconciliation checks |

- **Catch-up and backfill.** The daily and weekly DAGs create one run per missed interval. Each successful extract records its window in a coverage ledger, and a gap report lists gaps and overlaps. A cleared run rewrites its own raw keys, so a backfill does not duplicate rows.
- **Quality gate.** A failed Bronze or Silver check blocks the next layer, also on a later refresh with no new raw objects.
- **One writer at a time.** `transform_lakehouse` runs one at a time and shares a pool with `reconcile_gold`. Manual `make live-*` targets must not run while the DAGs do.

## Batch and streaming

The platform keeps three update paths apart; streaming does not replace batch ([ADR-0014](https://github.com/FilipeOliveira94/open-data-platform/blob/main/docs/decisions/0014-batch-vs-streaming-coexistence.md)).

| Path | How | Status |
| --- | --- | --- |
| Daily batch | Windowed PostgreSQL extract of the previous UTC day | Verified (Phase 3) |
| Weekly batch | Re-extract of the previous week for late commits; Silver keeps one row per key | Verified (Phase 3) |
| Streaming CDC | PostgreSQL logical replication, Debezium, Kafka, Spark Structured Streaming | **Planned (Phase 4)** |

The batch path cannot see a hard delete at the source: a deleted row is never extracted, so it stays in Silver and Gold. Capturing deletes is the job of the CDC path. No exactly-once claim is made for any path.
