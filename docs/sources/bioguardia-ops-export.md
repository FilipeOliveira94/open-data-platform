# BioGuardia Operations Hub daily export

| Field | Value |
| --- | --- |
| Name | BioGuardia Operations Hub daily export |
| Type | Generated daily file drop (gzip CSV and JSON Lines) with a manifest |
| Role | Operational data of a fictitious environmental agency in the Atlantic Forest: master data, field operations, monitoring, restoration, and control tables |
| URL | None. The generator is local (`open_data_platform.simulators.bioguardia`) |
| Gold Domain | Planned in Phase 11: wildfire response, biodiversity monitoring, watershed monitoring, restoration and carbon, field operations, reconciliation (P11-13, P11-14, P11-12) |
| License | Generated by this repository. IBGE municipality codes and names are public reference data |
| Access | MinIO bucket `odp-landing`, prefix `bioguardia_ops/`; Compose service `bioguardia-ops-export` (profile `sources`) or `make bioguardia-export` |
| Decision | [ADR-0027](../decisions/0027-bioguardia-synthetic-sources.md); domain model in [`bioguardia-domain.md`](../architecture/bioguardia-domain.md) |
| Related Issue | P11-02 (generator); P11-05 and P11-06 (ingestion, not built) |

Every value comes from one deterministic world model ([domain model](../architecture/bioguardia-domain.md)). The same seed, scale, export date, and version give the same rows; the gzip bytes are also the same with the same zlib build (gzip `mtime` is 0). Personal data is synthetic and cannot be a real person's: CPF and CNPJ carry wrong check digits, emails use the reserved `.example` domain, and phones use area codes ANATEL has not assigned.

## Layout and release

```text
odp-landing/bioguardia_ops/export_date=YYYY-MM-DD/export_version=N/
  _manifest.json
  <table>.csv.gz | <table>.jsonl.gz
  _SUCCESS
```

- `export_date` is the agency's local business day, `[D 00:00-03:00, D+1 00:00-03:00)`. Every timestamp carries the `-03:00` offset.
- Version 1 of date D is released at D+1 02:00 BRT. On about one date in 20 a version 2 is released three days later (D+4 02:00 BRT) in `export_version=2/`: a full re-delivery of every table of D with about 1% of `incidents` and `fire_hotspots` rows and 0.1% of `acoustic_detections` rows corrected, and any planted file defect of version 1 fixed. The corrected keys are in the planted list.
- `_SUCCESS` is written after the manifest, which is written after every table file. A drop without `_SUCCESS` is incomplete; the service regenerates it.
- The service never publishes a drop before its release time. The CLI does with `--allow-future`: the drops from 2026-11-26 to 2026-12-31 were written in advance on 2026-11-26, so they are visible before their release time. A reader must not take a drop whose manifest `released_at` is still in the future.
- A normal day has 21 tables; the first day of each month adds `canopy_surveys` (22). The manifest lists the tables a drop holds.
- From `ODP_BIOGUARDIA_SCHEMA_V2_FROM` (default 2026-12-15) `devices` gains `power_source` and its `schema_version` becomes 2.
- CSV: UTF-8, header row, comma separator, quotes only where needed (RFC 4180 quoting), LF line endings; notes can span lines inside quotes. JSON Lines: one object per line, decimal values as strings.

## Manifest

`_manifest.json` holds the source, export date and version, release time, generator version, seed, scale, and one entry per table: file name, format, change type, key, schema version, rows, bytes, uncompressed bytes, SHA-256, columns and types, control totals (exact decimal sums of the columns that carry money or measures), and the range of the table's time column. The manifest always describes the complete files. A planted truncated file has fewer bytes and a different SHA-256 than its manifest entry; a planted missing file is listed but absent. `_SUCCESS` holds the table count and the manifest's SHA-256.

## Planted defects

Defects are on by default (`ODP_BIOGUARDIA_DEFECTS=default`; `off` disables them and the version 2 re-deliveries). Each drop's list of what was planted (keys and defect types, no values) is written to the bucket `odp-evaluation` at `bioguardia_ops/export_date=D/export_version=V/planted.json`. The ingestion never reads that bucket; tests and evidence compare their findings to it.

| Level | Defect | Rate |
| --- | --- | --- |
| File | `truncated_file`: one table file cut to 60 to 90% of its bytes | About one date in 30 (version 1 only) |
| File | `missing_file`: one table listed in the manifest but not written | About one date in 45 (version 1 only) |
| Drop | `export_version=2` re-delivery with corrections | About one date in 20 |
| Record | Invalid values, malformed timestamps, nulls in required fields, exact and conflicting duplicate keys, orphan foreign keys | Per table, from 0.002% (big tables) to 0.4%; listed per row |
| Record | Personal data planted in `incidents.notes` and `citizen_reports.description` | About 4% of rows; listed with the PII types |

## Command

From the repository root, with MinIO up (`make up`):

```bash
make sources-build
# Publish a range now (dates after today need --allow-future).
make bioguardia-export START=2026-11-26 END=2026-12-31 WORKERS=8 ARGS=--allow-future
# Or run the export service, which publishes each day after its release time.
make sources-up
```

`python -m open_data_platform.simulators.bioguardia export generate --start … --end … --target-dir DIR` writes the same drops to a local directory instead of the buckets.

| Variable | Default | Meaning |
| --- | --- | --- |
| `ODP_BIOGUARDIA_SEED` | 7 | World seed |
| `ODP_BIOGUARDIA_SCALE` | 1 | Multiplies entity counts (about 24M rows per drop at 1) |
| `ODP_BIOGUARDIA_DEFECTS` | default | `off` disables planted defects |
| `ODP_BIOGUARDIA_SCHEMA_V2_FROM` | 2026-12-15 | First date of `devices` schema version 2 |
| `ODP_BIOGUARDIA_HISTORY_START` | 2026-11-26 | First date the export service publishes |
| `ODP_BIOGUARDIA_MAX_DROP_BYTES` | 2000000000 | A drop whose gzip files exceed it fails and publishes nothing |
| `ODP_LANDING_BUCKET`, `ODP_EVALUATION_BUCKET` | odp-landing, odp-evaluation | Target buckets |
